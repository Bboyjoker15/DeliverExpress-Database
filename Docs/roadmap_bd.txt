--------------------------------------------------------------------------
 0. REGLAS GENERALES (para los dos)
--------------------------------------------------------------------------
- PostgreSQL 16, instalado local en cada PC. Nada de Supabase ni nube.
- Base de datos: deliverexpress   Esquema: deliverexpress
- Zona horaria de la base: America/Caracas
    ALTER DATABASE deliverexpress SET timezone TO 'America/Caracas';
- La fuente de verdad son los scripts del repositorio (carpeta database/).
  Nadie crea ni cambia tablas "a mano" en pgAdmin sin pasarlo al script.
- Antes de subir a GitHub: ejecutar ejecutar_todo.sql desde cero sin errores.
- Cada integrante SOLO edita sus scripts (ver seccion 2).
- Cambiar una tabla de 01_esquema_tablas.sql se AVISA al grupo antes.
- Dinero: NUMERIC(10,2). Fechas: TIMESTAMPTZ. Coordenadas: NUMERIC(9,6).
- Moneda: todos los precios se guardan en USD. El cliente paga en USD o en
  bolivares (VES); se guarda la tasa BCV del dia y el total en bolivares.
  Si paga en USD se cobra IGTF 3%. IVA general 16%; productos exentos 0%.
- Nombres: snake_case, tablas en singular.
    PK = id_<tabla>      FK = mismo nombre que la PK que referencia
    Funciones fn_   Triggers trg_   Funciones de trigger fn_trg_
    Vistas vw_      Indices idx_<tabla>_<columnas>
    Restricciones pk_, fk_, ck_, uq_ + tabla + detalle
- Errores de negocio: toda funcion que falle lanza
    RAISE EXCEPTION 'CODIGO: descripcion en espanol';
  El backend lee el CODIGO. Codigos permitidos (no inventar otros):
    DIRECCION_INVALIDA        la direccion no existe o no es del cliente
    RESTAURANTE_NO_DISPONIBLE inactivo, cerrado o no cubre la zona
    PRODUCTO_INVALIDO         no existe, otro restaurante, no disponible o cantidad <= 0
    FUERA_DE_COBERTURA        la distancia no entra en ninguna tarifa
    TRANSICION_INVALIDA       cambio de estado no permitido
    REPARTIDOR_NO_ASIGNADO    se intenta pasar a en_camino sin repartidor
    REPARTIDOR_NO_DISPONIBLE  reasignacion manual a un repartidor no libre
    OFERTA_NO_PENDIENTE       se responde una oferta ya respondida o expirada
    CALIFICACION_NO_PERMITIDA pedido no entregado o calificacion repetida
    EMAIL_REPETIDO            registro con un email que ya existe
    TASA_BCV_NO_REGISTRADA    no hay ninguna tasa BCV cargada para esa fecha ni antes
    FACTURA_INMUTABLE         se intenta modificar o borrar una factura
    FACTURA_YA_ANULADA        se intenta anular una factura ya anulada o una nota de credito

 5. FUNCIONES DE LOGISTICA (03_funciones_logistica.sql) - INTEGRANTE 2
--------------------------------------------------------------------------
fn_param_num(p_clave VARCHAR) RETURNS NUMERIC
  Devuelve parametro_sistema.valor convertido a numero.

fn_distancia_km(p_lat1 NUMERIC, p_lon1 NUMERIC, p_lat2 NUMERIC, p_lon2 NUMERIC)
  RETURNS NUMERIC   IMMUTABLE
  Formula de Haversine, radio de la Tierra 6371 km, redondeado a 2 decimales.

fn_costo_envio(p_distancia NUMERIC) RETURNS NUMERIC
  Busca en tarifa_envio el rango km_desde <= distancia < km_hasta.
  Si no hay rango: FUERA_DE_COBERTURA.

fn_restaurante_disponible(p_id_restaurante INT, p_id_direccion INT) RETURNS BOOLEAN
  TRUE solo si: restaurante activo, tiene horario para el dia de hoy
  (EXTRACT(DOW FROM now())), la hora actual esta entre apertura y cierre,
  y la zona de la direccion esta en restaurante_zona.

fn_tasa_bcv(p_fecha DATE) RETURNS NUMERIC
  Tasa de esa fecha; si no hay (fin de semana, feriado), la ultima anterior.
  Si no hay ninguna: TASA_BCV_NO_REGISTRADA.

fn_tiempo_estimado(p_id_pedido INT) RETURNS INT
  minutos = tiempo_prep_min del restaurante
          + distancia_km / velocidad del vehiculo * 60
  Si el pedido no tiene repartidor, usar velocidad_moto_kmh.
  Redondear hacia arriba (CEIL).

fn_cotizar_pedido(p_id_cliente INT, p_id_restaurante INT, p_id_direccion INT,
                  p_productos JSONB, p_propina NUMERIC, p_moneda CHAR(3))
  RETURNS TABLE(distancia_km, subtotal, costo_envio, propina, iva_total, igtf,
                total, tasa_bcv, total_ves)
  Calcula todo SIN guardar nada. La usa el checkout para mostrar el total y
  la usa fn_crear_pedido (asi el calculo esta en un solo lugar).
  Formato de p_productos: [{"id_producto": 3, "cantidad": 2}, ...]
  Pasos:
   1. La direccion existe y es del cliente         -> si no DIRECCION_INVALIDA
   2. fn_restaurante_disponible                     -> si no RESTAURANTE_NO_DISPONIBLE
   3. Cada producto existe, es del restaurante, disponible, cantidad > 0,
      y la lista no esta vacia                      -> si no PRODUCTO_INVALIDO
   4. distancia = fn_distancia_km(restaurante -> direccion)
      costo_envio = fn_costo_envio(distancia)
   5. subtotal = suma de cantidad * precio
      base_16 = suma de productos NO exentos + costo_envio
      iva_total = ROUND(base_16 * iva_general, 2)
      igtf = si p_moneda = 'USD': ROUND((subtotal + costo_envio + propina + iva_total) * igtf, 2)
             si no: 0
      total = subtotal + costo_envio + propina + iva_total + igtf
      tasa_bcv = fn_tasa_bcv(current_date)
      total_ves = ROUND(total * tasa_bcv, 2)

fn_crear_pedido(p_id_cliente INT, p_id_restaurante INT, p_id_direccion INT,
                p_productos JSONB, p_propina NUMERIC, p_moneda CHAR(3),
                p_ultimos4 CHAR(4))
  RETURNS INT  (id_pedido)
  Pasos:
   1. SELECT * FROM fn_cotizar_pedido(...)  (hace todas las validaciones)
   2. comision_plataforma = ROUND(subtotal * comision_plataforma, 2)
      monto_restaurante = subtotal - comision_plataforma
      (la comision es sobre productos SIN IVA)
   3. INSERT pedido (estado 1, con moneda_pago, tasa_bcv_aplicada, iva_total,
      igtf, total_ves), INSERT detalle_pedido,
      INSERT pago (monto = total, moneda = p_moneda,
                   referencia = 'SIM-' || id_pedido || '-' || to_char(now(),'YYYYMMDDHH24MISS'))
   4. UPDATE tiempo_estimado_min = fn_tiempo_estimado(id_pedido)
  Todo ocurre en la misma transaccion: si algo falla, no queda nada.
  La factura NO se crea aqui: se crea al entregar (seccion 8b).

fn_cambiar_estado(p_id_pedido INT, p_nuevo_estado SMALLINT, p_id_usuario INT,
                  p_motivo VARCHAR DEFAULT NULL) RETURNS VOID
  UNICA forma de cambiar el estado de un pedido (el backend no hace UPDATE directo).
   1. PERFORM set_config('deliverexpress.id_usuario', p_id_usuario::text, true);
      (el trigger de historial lee ese valor con current_setting(..., true))
   2. Si p_nuevo_estado = 4 y el pedido no tiene repartidor -> REPARTIDOR_NO_ASIGNADO
   3. UPDATE pedido SET id_estado (y motivo_cancelacion si es 6)
      (la validacion de la transicion la hace el trigger)
   4. Si p_nuevo_estado = 2: PERFORM fn_asignar_repartidor(p_id_pedido)
      (el repartidor se busca cuando el restaurante acepta el pedido)
   5. Si p_nuevo_estado = 6: las ofertas pendientes de ese pedido pasan a 'expirada'

fn_asignar_repartidor(p_id_pedido INT) RETURNS INT  (id_repartidor ofertado o NULL)
  Si el pedido ya tiene repartidor o ya tiene una oferta pendiente: devuelve NULL.
  Candidatos:
   - activo = TRUE y disponibilidad = 'libre' y con ubicacion (latitud_actual NOT NULL)
   - su id_zona esta en las zonas que cubre el restaurante (restaurante_zona)
   - NO tiene otra oferta pendiente
   - NO rechazo ni dejo expirar una oferta de ESTE pedido
  Orden: prioridad 'normal' primero, luego menor distancia al restaurante,
         luego mayor calificacion_promedio.
  Esqueleto obligatorio (control de concurrencia):
     SELECT r.id_repartidor, fn_distancia_km(...) AS dist
     FROM repartidor r ...
     WHERE ...
     ORDER BY (r.prioridad = 'baja'), dist, r.calificacion_promedio DESC
     LIMIT 1
     FOR UPDATE OF r SKIP LOCKED;
  Si hay candidato: INSERT oferta_asignacion (pendiente) y devolver su id.
  Si no hay: devolver NULL (el coordinador lo ve como "sin repartidor").

fn_responder_oferta(p_id_oferta INT, p_acepta BOOLEAN) RETURNS INT
  Si la oferta no esta 'pendiente' -> OFERTA_NO_PENDIENTE
  Acepta:  oferta 'aceptada' + fecha_respuesta; pedido.id_repartidor = repartidor;
           repartidor.disponibilidad = 'ocupado';
           recalcular pedido.tiempo_estimado_min; devuelve id_repartidor.
  Rechaza: oferta 'rechazada' + fecha_respuesta;
           devuelve fn_asignar_repartidor(id_pedido) (siguiente candidato o NULL).

fn_expirar_ofertas() RETURNS INT  (cantidad de ofertas expiradas)
  El backend la llama cada 30 segundos.
   1. Ofertas pendientes con mas de oferta_expira_seg -> 'expirada' + fecha_respuesta
   2. Para cada pedido en estado 2 o 3 sin repartidor y sin oferta pendiente:
      PERFORM fn_asignar_repartidor(id_pedido)

fn_reasignar_pedido(p_id_pedido INT, p_id_repartidor INT, p_id_usuario INT) RETURNS VOID
  Uso del coordinador. Solo pedidos en estado 2 o 3.
   - Si el pedido tenia repartidor: ese repartidor vuelve a 'libre'.
   - Ofertas pendientes del pedido -> 'expirada'.
   - Si p_id_repartidor es NULL: pedido sin repartidor y PERFORM fn_asignar_repartidor.
   - Si no es NULL: el repartidor debe estar 'libre' (si no REPARTIDOR_NO_DISPONIBLE);
     se asigna directo y pasa a 'ocupado'.

fn_registrar_ubicacion(p_id_repartidor INT, p_latitud NUMERIC, p_longitud NUMERIC)
  RETURNS VOID
  INSERT en ubicacion_repartidor con id_pedido = pedido activo del repartidor
  (estado 2, 3 o 4 y id_repartidor = el suyo), o NULL si no tiene.

 8b. FACTURACION (08_facturacion.sql) - INTEGRANTE 1
--------------------------------------------------------------------------
Que se factura:
  - factura_cliente   automatica cuando el pedido pasa a entregado
  - factura_comision  a cada restaurante por la comision del 15% de un periodo, + IVA 16%
  - nota_credito      anula una factura (devolucion o error)
  - liquidacion_repartidor  pago de envios + propinas de un periodo (no es factura fiscal)
Fuera del alcance: retenciones de IVA/ISLR, libro de compras, autorizacion
del SENIAT y PDF con validez legal.

Numeracion SIN huecos:
  Las facturas deben ser correlativas. Un SEQUENCE puede dejar huecos si una
  transaccion falla, por eso se usa la tabla correlativo con bloqueo de fila:

fn_siguiente_correlativo(p_punto_venta SMALLINT)
  RETURNS TABLE(numero_factura VARCHAR, numero_control VARCHAR)
    UPDATE correlativo SET ultimo_numero = ultimo_numero + 1,
                           ultimo_control = ultimo_control + 1
    WHERE punto_venta = p_punto_venta
    RETURNING lpad(punto_venta::text, 4, '0') || '-' || lpad(ultimo_numero::text, 8, '0'),
              lpad(punto_venta::text, 2, '0') || '-' || lpad(ultimo_control::text, 6, '0');
  (el UPDATE bloquea la fila: dos facturas simultaneas esperan su turno.
   Si la transaccion falla, el numero se devuelve con el ROLLBACK: no hay huecos.
   Facturas y notas de credito comparten la misma serie: es una simplificacion.)

fn_emitir_factura_cliente(p_id_pedido INT, p_fecha TIMESTAMPTZ DEFAULT now())
  RETURNS INT (id_factura)
  - Receptor: el cliente; rif_receptor = cedula_rif (puede ser NULL),
    razon_social_receptor = nombre del cliente
  - Emisor: parametros emisor_*
  - moneda = pedido.moneda_pago, tasa_bcv = pedido.tasa_bcv_aplicada
  - Lineas de detalle:
      una por producto (alicuota 0 si exento_iva, si no 16)
      "Servicio de envio"          alicuota 16
      "Propina para el repartidor" alicuota 0, no_sujeto = TRUE (si propina > 0)
  - Totales de la cabecera iguales a los del pedido (iva_16 = iva_total, igtf, total, total_ves)
  - p_fecha existe para poder facturar los pedidos historicos de los datos de prueba

trg_facturar_pedido   AFTER UPDATE OF id_estado ON pedido
  Si el nuevo estado es 5 (entregado): PERFORM fn_emitir_factura_cliente(NEW.id_pedido)

fn_anular_factura(p_id_factura INT, p_motivo VARCHAR, p_id_usuario INT)
  RETURNS INT (id de la nota de credito)
  - La factura debe ser factura_cliente o factura_comision en estado 'emitida',
    si no FACTURA_YA_ANULADA
  - Crea una nota_credito con el mismo receptor, montos y lineas que la original,
    id_factura_afectada = la original, observaciones = p_motivo
  - Pone la original en estado 'anulada'
  - Si es factura_cliente: pago.estado = 'reembolsado'
  (Uso tipico: devoluciones de pedidos, que el cliente dijo que eran el 10%)

fn_generar_facturas_comision(p_desde DATE, p_hasta DATE, p_id_usuario INT)
  RETURNS INT (cantidad de facturas creadas)
  Para cada restaurante con pedidos entregados en el periodo que todavia no
  esten en una factura_comision emitida:
  - Una factura con una linea por pedido: "Comision 15% pedido #N",
    base = comision_plataforma, alicuota 16
  - moneda 'USD', tasa_bcv = fn_tasa_bcv(current_date), igtf 0
  - Receptor: el restaurante (rif, razon_social, direccion_fiscal)
  Si un restaurante no tiene pedidos en el periodo, no se le factura.

fn_generar_liquidaciones(p_desde DATE, p_hasta DATE)
  RETURNS INT (cantidad de liquidaciones creadas)
  Para cada repartidor con pedidos entregados en el periodo que no esten en
  detalle_liquidacion: crea la liquidacion (numero LIQ-NNNNNNNN usando el
  id_liquidacion) y una fila de detalle por pedido.

Inmutabilidad:
trg_factura_inmutable          BEFORE UPDATE OR DELETE ON factura
  - DELETE: siempre FACTURA_INMUTABLE
  - UPDATE: solo se permite cambiar estado de 'emitida' a 'anulada';
    cualquier otro cambio -> FACTURA_INMUTABLE. Forma sencilla de comprobarlo:
      IF (to_jsonb(NEW) - 'estado') IS DISTINCT FROM (to_jsonb(OLD) - 'estado')
         OR NOT (OLD.estado = 'emitida' AND NEW.estado = 'anulada') THEN ...
trg_detalle_factura_inmutable  BEFORE UPDATE OR DELETE ON detalle_factura
  - siempre FACTURA_INMUTABLE
trg_liquidacion_inmutable      BEFORE UPDATE OR DELETE ON liquidacion_repartidor
                               y ON detalle_liquidacion
  - siempre FACTURA_INMUTABLE
